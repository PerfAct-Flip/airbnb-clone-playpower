Vacation Rental Marketplace — Production-Scale Architecture

Scaling strategy for frontend, backend, storage, search, and deployment

Clients
Web (Next.js) SSR for SEO-critical listing pages, ISR (revalidate on price/availability change) so listing pages don't hit origin on every request
Mobile apps (iOS / Android) Talk to the same public API layer as web — no separate mobile-only backend
↓
Edge / CDN
CDN (static assets + images) Listing photos served resized/optimized at the edge; scales reads horizontally without touching origin storage
Edge cache for listing pages Cached HTML for anonymous browsing (the overwhelming majority of traffic); cache key includes locale/currency, invalidated on listing update
↓
API Gateway
Gateway / BFF Auth (JWT verification), per-IP and per-user rate limiting, request routing to services below — the single scaling bottleneck to watch, so it's stateless and scaled horizontally behind a load balancer independent of the services it fronts
↓
Core Services (independently deployed and scaled)
ListingsCRUD, availability calendar
Scales with read replicas — read-heavy, write-light
SearchGeo + text + filters
Scales as an Elasticsearch cluster, sharded by region
BookingReservation + date-hold logic
The concurrency-critical service — see flow note below
PricingDynamic pricing, fees
Stateless, scales trivially behind the gateway
PaymentsStripe/provider integration
Isolated service to keep PCI scope small
ReviewsPost-stay ratings
Read-heavy, cached aggressively per listing
Messaging / NotificationsHost↔guest chat, transactional email
WebSocket-based chat; async email/SMS via queue workers
IdentityAuth, host/guest profiles
Single source of truth for user identity across services
Booking concurrency: the same problem as a seat-booking system — two guests must never book the same listing for overlapping dates. The Booking service holds a short-lived reservation (row-level lock or an optimistic version column on the availability row) before confirming payment, so a double-booking fails fast with a clear conflict instead of corrupting state.
↓
Data & Messaging
PostgreSQLSource of truth
Sharded by region at extreme scale; read replicas per service that needs them
RedisCache, sessions, rate limits
Hot availability lookups and search-result caching live here, not in Postgres
ElasticsearchSearch index
Never dual-written from app code — kept in sync via CDC below
Object storage (S3-compatible)Listing photos, documents
Origin behind the CDN layer above
Event bus (Kafka/SQS)Async backbone
Booking confirmations, notification jobs, analytics events
Search sync: a CDC pipeline (e.g. Debezium) streams Postgres listing/availability changes onto the event bus, which a consumer applies to Elasticsearch. This avoids the classic dual-write bug where a listing update succeeds in Postgres but silently fails to reach the search index.
↓
Deployment & Operations
Kubernetes, multi-regionEach service autoscales independently on its own load signal (Booking on request latency, Search on query volume, etc.)
CI/CDPer-service pipelines; canary or blue/green rollout so a bad Booking-service deploy doesn't take down Search
ObservabilityPrometheus metrics + OpenTelemetry distributed tracing across all services, so one slow booking request can be traced end-to-end from gateway through to Postgres
Why this shape: the two things that actually break at scale for a marketplace like this are (1) search falling out of sync with the source of truth, and (2) double-booking under concurrent demand for the same dates — both are called out explicitly above with their specific mitigation, rather than left implicit in a generic "microservices + database" box diagram.
